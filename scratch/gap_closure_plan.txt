1. Current Ultron: the truth we are starting from
The supplied project context describes Ultron as a local-first, permission-gated, tool-using Python CLI. The
snapshot contains a mature set of capabilities: a ReAct agent, 38 registered tools, security gating,
memory/knowledge graph, retrieval, planning, parallel tool execution, structured-output validation,
resource monitoring, API schema learning, debugging context, multimodal scaffolding, and a responsive
CLI.
<b>Important repository inconsistency:</b> the handoff context describes some components as
implemented while the supplied source snapshot still contains scaffolds. For example,
<code>core/intelligence/model_catalog.py</code> is a placeholder in the snapshot, and
<code>agents/orchestrator.py</code>, <code>codeact.py</code>, <code>operative.py</code>, and
<code>monitor.py</code> are explicitly scaffold files. The plan therefore starts with a truth audit rather
than blindly assuming either the documentation or previous conversation state is correct.

2.1 Architectural invariants
●
 One authoritative TaskState owns task lifecycle. No subsystem invents a second hidden task state.
●
 Every meaningful agent action produces a typed event or an auditable record.
●
 Tools are capabilities, not workflow logic. Planning, verification, retry, and repair belong above tools.
●
 The model may propose an action; only the runtime can authorize and execute it.
●
 Security is evaluated on canonicalized actions, not raw model text.
●
 Context is assembled by a dedicated ContextManager under a token budget; the agent never blindly
sends the entire history.
●
 Repository retrieval is deterministic/reproducible enough to debug: every retrieved context item has a
reason/source.
●
 Autonomous modification must be recoverable through checkpoints or Git.
●
 Completion is decided by verification evidence and TaskState, never by the model saying 'done'.
●
 No phase may weaken existing security behavior or silently broaden file/network permissions.

4. Phase 1 — Canonical TaskState + Event Model
<b>Goal:</b> Create one durable runtime state model and an event stream that can explain everything
the agent did.
<b>Primary modules:</b> core/types.py, new core/runtime/, core/state.py, agents/base.py,
tools/registry.py, security/audit.py.
<b>Implementation work:</b>
●
 Define typed events: UserRequest, TaskCreated, PlanCreated, ModelSelected, ContextBuilt,
ToolRequested, ToolAuthorized, ToolStarted, ToolCompleted, ToolFailed, VerificationStarted,
VerificationPassed, VerificationFailed, RepairStarted, RepairCompleted, CheckpointCreated,
TaskCompleted, TaskFailed, TaskCancelled.
●
 Define TaskState fields: task_id, goal, status, plan, current_step, attempts, requirements, evidence,
checkpoints, errors, timestamps, model decisions.
●
 Make event IDs, task IDs, and action IDs stable and unique.
●
 Ensure state transitions are explicit and validated.
●
 Persist events using a simple append-only JSONL or SQLite backend first; abstract the storage interface.
●
 Make the runtime replayable: rebuilding TaskState from events must reproduce the same state.
●
 Do not put model reasoning text into security audit records unless explicitly needed; avoid secret
leakage.
<b>Required validation:</b>
●
 Unit tests for every state transition.
●
 Replay test: execute task → persist events → rebuild state → compare state.
●
 Failure/retry/cancel tests.
●
 Backward compatibility tests for current ReAct and SimpleAgent behavior.
<b>Exit criteria:</b> A task can be stopped, restarted, inspected, and replayed without losing its
authoritative state.
<b>Known risk:</b> Do not introduce a database migration dependency unless the existing persistence layer requires it.

5. Phase 2 — Context Manager + Token Budgeting
<b>Goal:</b> Stop context-window failures from being accidental runtime failures.
<b>Primary modules:</b> New core/context/, agents/react.py, prompt_assembly.py, types/history
handling.
<b>Implementation work:</b>
●
 Create ContextManager with a hard token/character budget.
●
 Separate static system instructions, task state, recent conversation, repository context, tool
observations, verification evidence, and long-term memory.
●
 Implement deterministic context priority: current task > active plan step > latest failure > relevant
repository context > recent dialogue > older history.
●
 Implement condensation/summarization for long histories.
●
 Track token budget before every model call.
●
 When a context build cannot fit, reduce lower-priority material instead of sending an oversized prompt.
●
 Record ContextBuilt events containing counts/IDs/estimated sizes, not sensitive raw content.
●
 Add model-specific context limits to ModelCatalog/ModelRouter.
<b>Required validation:</b>
●
 Synthetic long conversation test exceeding the model budget.
●
 Nested tool-output stress test.
●
 Context condensation preserves task goal, current step, failure evidence, and important decisions.
●
 No model call exceeds configured context budget.
●
 Regression test for the previously observed oversized ReAct prompt.
<b>Exit criteria:</b> Long-running tasks remain executable under bounded context.
<b>Known risk:</b> Do not solve context overflow by simply increasing the model context length.
6. Phase 3 — Repository Intelligence / Repo Map
<b>Goal:</b> Give Ultron Aider-class repository awareness without dumping the entire repository into
the prompt.
<b>Primary modules:</b> New core/repository/, retrieval.py, context manager, file tools.
<b>Implementation work:</b>
●
 Build a repository index for files, languages, symbols, imports, references, tests, configuration files, and
generated/ignored paths.
●
 Use tree-sitter or another reliable parser where available; provide graceful fallback for unsupported
languages.
●
 Build symbol and dependency relationships.
●
 Implement RepoMap generation under a configurable token budget.
●
 Implement task-aware retrieval using lexical match + symbol match + dependency proximity +
recent-change relevance.
●
 Always return provenance: file, symbol/region, relevance reason.

 Exclude secrets, build artifacts, virtual environments, caches, and Git internals by default.
●

7. Phase 4 — Typed Tool/Action/Observation Runtime
<b>Goal:</b> Turn tool calling into a reliable execution protocol rather than direct function dispatch.
<b>Primary modules:</b> core/tools/, new core/runtime/actions.py, observations.py, executor.py,
security boundary.
<b>Implementation work:</b>
●
 Define ToolDefinition: name, input schema, output schema, risk metadata, read-only metadata,
idempotency metadata, timeout, concurrency policy.
●
 Define ActionRequest and ActionResult/Observation types.
●
 Canonicalize tool names before security checks.
●
 Validate model arguments against schemas before execution.
●
 Normalize malformed tool calls and return structured errors to the model.
●
 Separate authorization from execution.
●
 Add timeout/cancellation support.
●
 Capture stdout/stderr/exit status for process tools as structured observations.
●
 Keep tool implementations small; move orchestration logic into the runtime.
<b>Required validation:</b>
●
 Malformed JSON/tool argument tests.
●
 Unknown tool tests.
●
 Schema mismatch tests.
●
 Timeout/cancellation tests.
●
 Security canonicalization tests.
●
 Observation serialization/replay tests.
<b>Exit criteria:</b> Every tool call follows the same request → authorize → execute → observe lifecycle.
<b>Known risk:</b> Existing security decisions must remain at least as restrictive as before.

8. Phase 5 — Verification Engine + Autonomous
Repair
<b>Goal:</b> Make edit/test/diagnose/repair a first-class control loop.
<b>Primary modules:</b> New core/verification/, core/intelligence/debug_context.py, task planning,
ReAct agent.
<b>Implementation work:</b>
●
 Define VerificationSpec: commands, expected exit codes, expected files, assertions, and completion
requirements.
●
 After modifications, automatically determine whether verification is required.
●
 Run the smallest relevant verification first; expand to broader tests when necessary.
●
 Normalize failures into FailureEvidence: command, exit code, stderr, traceback, affected files, likely
subsystem.
●
 Feed FailureEvidence into the debug context and ContextManager.
●
 Create RepairController with bounded attempts and explicit stop reasons.
●
 Detect repeated identical failures and prevent infinite loops.
●
 Completion requires positive verification evidence when the task is marked verifiable.
<b>Required validation:</b>
●
 Fix a deterministic failing test end-to-end.
●
 Repair a syntax error.
●
 Repair a dependency/import error.
●
 Repair a behavioral assertion failure.
●
 Repeated failure stops after configured limit.
●
 Model claiming success without verification does not complete the task.
<b>Exit criteria:</b> Ultron can autonomously perform bounded repair cycles and explain why it
stopped.
<b>Known risk:</b> Do not allow the repair loop to modify security policy, credentials, or unrelated files merely to make
tests pass.

 Support rollback to task checkpoint.
●
 Protect unrelated pre-existing user changes; never blindly reset the entire worktree.

●

●

 Host backend regression suite.
●
 Sandbox backend contract suite.

13. Phase 10 — Delegation/Subagents and Advanced
Agent Modes

<b>Primary modules:</b> core/agents/orchestrator.py, codeact.py, operative.py, monitor.py, new

 Implement OrchestratorAgent as a planner/delegator, not another independent runtime.

Do not skip ahead because a later feature is more exciting. In particular, do not implement subagents

accumulate multiple competing control loops and become harder to debug than the problems it is meant
to solve.

18. Validation strategy
Ultron should use a two-layer validation strategy. Layer 1 is deterministic software testing. Layer 2 is

19. Explicit non-goals for this upgrade
●
 Do not prioritize voice, phone control, desktop UI, web UI, or wake-word features until the coding
runtime is reliable.
●
 Do not create an uncontrolled multi-agent swarm.
●
 Do not add dozens of tools merely to increase the tool count.
●
 Do not replace deterministic safeguards with prompt instructions.
●
 Do not solve context problems by blindly increasing context length.
●
 Do not add a vector database before deterministic repository indexing/retrieval has been measured and
shown insufficient.
●
 Do not couple the core runtime to one model vendor or one inference backend.
●
 Do not remove existing tests simply because architecture changed; migrate them to the new contracts.
●
 Do not declare a phase complete because code exists. A phase is complete only when its exit criteria
and regression tests pass.
20. Coding-AI implementation protocol
Put this document in the project root and instruct the coding AI to treat it as the architecture plan. The
following protocol is intentionally strict so that an AI coding agent does not hallucinate implementation
status or redesign unrelated parts of Ultron.
Before changing code
●
 Read this PDF plus PROJECT_CONTEXT.md, README.md, AGENTS.md, docs/architecture.md, and the
relevant subsystem docs.
●
 Inspect the actual source files named by the phase.
●
 Run or inspect the baseline tests relevant to the phase.
●
 State what currently exists, what is partial, and what is missing.
●
 If the repository contradicts this document, do not guess. Record the discrepancy and adapt the
implementation to the actual code while preserving the target architecture.
While implementing
●
 Work on one phase at a time.
●
 Do not implement future-phase features opportunistically.
●
 Prefer small additive interfaces over large rewrites.
●
 Preserve existing security behavior.
●
 Add tests with every behavior change.
●
 Keep the repository lint-clean.
●
 Do not fabricate benchmark results, test counts, model capabilities, or implementation status.
After implementing
●
 Run the phase-specific tests.
●
 Run the full regression suite.

21. Final Definition of Done
Ultron's gap-closure program is complete when the system can take a repository-level coding request and
execute the following lifecycle reliably:
1. Understand the goal.
2. Inspect repository structure and relevant symbols.
3. Build a bounded, provenance-aware context.
4. Create/validate a task plan.
5. Select an appropriate model using hard constraints + deterministic scoring.
6. Propose typed actions.
7. Apply security policy before execution.
8. Execute safe/approved actions through an execution backend.
9. Record observations/events.
10. Verify the resulting state.
11. Diagnose failures using structured evidence.
12. Repair within bounded attempts.
13. Checkpoint/rollback changes when necessary.
14. Continue until verification proves completion or a clear stop condition is reached.
15. Persist enough state to resume/replay the task.
16. Produce a transparent final report of what changed and what was verified.
<b>The target is not maximum autonomy.</b> The target is bounded, inspectable autonomy: Ultron
should be able to do substantial coding work without constant babysitting while remaining recoverable,
secure, explainable, and deterministic enough to debug.
 End of architecture handoff.
